# Design

## Context

專案目前沒有應用程式程式碼或既有技術架構。需求涉及多個用戶端即時同步、同時提交順位、檔案匯入與回填，因此須先界定狀態來源、交易邊界與房間權限。使用者指定 Python 伺服端與服務層、HTML/CSS 頁面及 WebSocket；瀏覽器端需少量原生 JavaScript 才能連接 WebSocket 並更新頁面。

需求契約見 proposal.md 與 `specs/` 下五項能力規格。Guided Notes 範本為[單題範本](https://docs.google.com/spreadsheets/d/1dHJOnfihH0J2OPeqzkMofJD17TXMsT10PfVDbCqW7aQ/edit?usp=sharing)及[單題／題組範本](https://docs.google.com/spreadsheets/d/1PVb8svNsVaOeNAKjcXgUhrrEcTCbUp1PtoPh6ocPEJk/edit?usp=sharing)。目前檢視到兩份工作表均有題號、題目及作答欄；題組範本以同一題號涵蓋多列題目，並以 `(1)`、`(2)` 標示多個答案空格。匯入器需同時支援這種欄位結構及明確的 `[Q1]` 題號填空標籤。第一版假設老師上傳從 Google 試算表匯出的 `.xlsx` 檔案，並以 `.xlsx` 副本下載結果。

## Goals / Non-Goals

**Goals:**

- 以單一 Python 服務提供 HTTP 頁面/API 與 WebSocket，即時同步房間狀態。
- 讓伺服端成為提交時間、順位、題組勝負與每組獲勝題數的唯一權威來源。
- 在結果事件送出前完成資料持久化，讓重新連線的用戶端能取得目前完整狀態。
- 以單題與題組範本匯入題號、題組、題內答案空格，並輸出填妥的講義副本。
- 為學生、老師與投影視圖提供不同的資料範圍，確保進行中答案不外洩。

**Non-Goals:**

- 不建立使用者帳號、班級名冊、課程管理或長期學習分析平台。
- 第一版不直接連接 Google Drive API；以老師上傳的範本試算表檔案建立房間，並下載已填妥的檔案副本。
- 不依答案文字自動判分；答案有效性由老師人工審核。
- 不支援多伺服器水平擴展或跨程序 WebSocket 廣播。

## Decisions

### Python ASGI 應用程式提供頁面、API 與 WebSocket

採用 FastAPI 作為 Python ASGI 入口，HTML/CSS 提供頁面，使用原生 JavaScript 負責 WebSocket 連線、表單送出及 DOM 更新，不引入前端框架。FastAPI 官方文件提供 WebSocket 端點、依賴驗證與測試用戶端的支援，足以涵蓋此應用的雙向事件需求（[FastAPI WebSockets](https://fastapi.tiangolo.com/advanced/websockets/)、[Testing WebSockets](https://fastapi.tiangolo.com/advanced/testing-websockets/)）。

替代方案是使用獨立前端框架或另設 WebSocket 服務；目前沒有既有程式碼需要配合，額外服務會增加部署及狀態同步面，因此第一版採同一 ASGI 應用。

### 將業務規則置於服務層，傳輸層只做驗證與轉送

服務層負責建立房間、加入組別、階段轉換、提交驗證、題組原子仲裁、審核、遞補、上限計算及結果組裝。HTTP 路由與 WebSocket handler 呼叫相同服務層，避免同一規則因入口不同而產生差異。

替代方案是在 WebSocket handler 中直接執行競賽規則；此方式初期看似簡單，但會把傳輸細節與交易邏輯耦合，也較難驗證同時提交及 CSV 結果的一致性。

### 以 SQLite 交易序列化候選提交

第一版使用 SQLite 持久化房間、組別、題目與題組、提交答案、伺服器接收時間、單調遞增處理序列、審核狀態及結果。每個單題或題組提交在一個資料庫交易中驗證階段與重複狀態、配置序列、寫入完整答案，再提交交易。題組要嘛所有題目一起接受，要嘛全部拒絕。得主由有效候選依 `(received_at, receipt_sequence)` 順序計算；獲勝上限排除不合格組別後再遞補。資料庫唯一限制用來防止同組重複提交。

替代方案是用記憶體鎖決定先後；程序重啟會失去排名依據，且 WebSocket 廣播可能早於持久化。SQLite 單寫入者可能降低高併發吞吐量，但單一課堂房間規模優先需要可重現的順序與簡易部署。若日後需多程序或多節點，應改用具交易序列化能力的共用資料庫並加入跨節點事件代理。

### WebSocket 只傳遞已提交的狀態事件

提交先由 HTTP 或 WebSocket 命令呼叫服務層並完成交易，成功後才廣播事件。事件依角色及房間範圍過濾：組別僅收到自身「已送出」狀態與公共階段；老師收到所有提交與進度；學生只在活動結束後收到得主答案；投影端收到倒數視覺狀態、得主摘要與排行榜。重新連線時先取得服務層組裝的目前快照，再接收後續事件。

替代方案是讓前端自行推測提交成功與名次；網路重送或同時提交會造成畫面排序與伺服端不一致。伺服端交易結果作為廣播唯一來源，並用事件識別碼讓用戶端可忽略重複事件。

### 以角色化會話及組別租約限制重複視窗

老師建立房間後取得老師專用會話；學生以房間代碼及組名加入，系統核發組別視窗會話。伺服端同一房間同一組別只允許一個有效租約，不同視窗再次加入會被拒絕；同一視窗短暫斷線可用原會話恢復。資料查詢與 WebSocket 廣播均先檢查會話角色，學生連線不訂閱老師的提交明細頻道。會話識別資料不得寫入程式碼或一般日誌，部署密鑰透過環境設定提供。

替代方案是只靠前端按鈕停用或瀏覽器本機鎖；這無法防止直接重送或另一個裝置加入，因此限制必須由伺服端執行。第一版可使用短效租約處理斷線，實際逾時值在實作時以部署設定決定。

### 以解析器與回填器隔離 Guided Notes 格式

匯入器以解析器 adapter 讀取 `.xlsx` 工作簿，依題號欄、答案欄、同題號合併列及 `(1)`、`(2)` 空格標記建立內部模型；另支援明確的 `[Q1]` 類標籤。內部模型分開表示題號、題組提交單位與答案空格，因此一題可含多個答案欄位，多題亦可被綁為一次仲裁的題組。原始上傳檔案與每個答案空格的工作表／儲存格映射隨房間保存；匯出時複製原始檔並只寫入有有效得主的空格，無得主空格維持原狀。未辨識或缺漏標記在建立房間前回報，不猜測題號。第一版不在執行時要求 Google 帳戶或讀寫雲端文件。

替代方案是把題目另存成簡化 CSV；這會失去原講義版面與填空位置，無法符合回填需求。解析與回填分開，可在不改變競賽模型下修正範本映射。

### 以題目得主數計算排行榜，倒數採開始提示動畫

每題得主為組別增加一分；題組一次勝出時依其題數增加分數，題組不得拆分。組別分數相同時並列，不另設未確認的速度加權破平規則。投影倒數採開始提示動畫，不作為自動結束活動的計時器；活動開始與結束仍由老師控制。

替代方案是依總作答速度加權或倒數到零自動結束；需求沒有指定這些規則，而且可能與手動結束控制衝突，因此不納入第一版。

### 房間紀錄保留於本機資料庫

房間、提交及來源講義保存在部署端 SQLite 檔案，第一版不自動過期，也不提供產品內刪除流程；部署操作者可依課程資料政策手動清理。這讓老師能在活動後匯出紀錄，同時避免未定義的自動刪除期限。

## Risks / Trade-offs

- [單一程序的 WebSocket 連線與廣播無法跨多個工作程序] → 第一版限定單一應用程序；若部署拓展，新增共享事件代理並驗證跨節點快照與事件一致性。
- [SQLite 寫入鎖定可能造成提交延遲] → 將順位配置與答案寫入放在短交易內，交易完成後才做非同步廣播；記錄鎖定錯誤並提供用戶端明確重試狀態。
- [範本儲存格或空格標記解析錯誤會導致題數或回填位置錯誤] → 將兩份範本列為解析測試固定樣本；建立房間前顯示預覽題號與題組，匯出前驗證題號一對一映射。
- [組別租約可能在網路暫斷後阻擋立即重入] → 同一視窗保留會話以重連；在租約釋放前拒絕其他視窗加入。
- [學生端誤收到老師事件會洩露答案] → 以伺服端角色過濾事件，不依賴 CSS 隱藏；加入以多角色連線檢查事件負載的驗收測試。
- [上傳檔案可能過大或格式惡意] → 僅允許必要試算表格式、限制檔案大小、解析前驗證內容，並使用安全檔名保存。

## Migration Plan

本專案沒有既有應用程式或資料，無需遷移。首次部署建立資料庫結構與上傳檔案目錄；回復時停止服務並保留或移除該版本產生的資料，依課程資料保留決策處理。部署不得將任何密碼、金鑰或會話祕密寫入版本庫。
